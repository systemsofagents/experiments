# Cache-aware context without a cache API in the policy

**Decision:** Keep prompt caching out of the public context-policy API. A policy decides what evidence to send; the provider adapter decides how to mark reusable prefixes. The host reports observed cache usage separately from its local prefix comparison. No policy may retain revoked content, preserve stale instructions or exceed a context window to save a cache hit.

The prefix is the part of the rendered prompt before its first difference from an earlier request. New user turns and on-demand tool results append; they should not rewrite a block near the front. An early edit or compaction can cost us reuse from the first changed token onward, but should leave a genuinely unchanged earlier prefix eligible. Compaction trades a possible one-time miss or rewrite for a smaller working window; caching reuses computation and does not increase that window. Neither is storage, authorization or a substitute for a recoverable transcript. If the window still fits, compact for cost only when savings on the expected remaining turns justify the compaction call, new writes and forgone reads.

On newer OpenAI frontier models, changing an earlier item can also remove later reasoning items, not just reduce cache reuse. Inspect `input_transformations` for `prefix_mismatch`. Documented OpenAI compaction paths preserve subsequent reasoning despite their prefix change; a home-grown prefix rewrite does not have that guarantee. See [prefix continuity](https://developers.openai.com/api/docs/guides/keep-prefix-unchanged).

## Payload shape

Arrange content in decreasing order of expected stability, within the provider's message-order rules:

1. **Stable:** canonical tool schema order and fixed instructions. Give these a separate writable cache boundary if the adapter supports it and the prefix clears the model's minimum. Do not include clocks, request identifiers, retrieval rankings or mutable facts here.
2. **Per context version:** validated brief or provider-native continuation. Do not regenerate an equivalent brief or reserialize ordered wire items every turn. Install a new version only at a legal boundary, and treat old-prefix reuse as uncertain.
3. **Append-only within a context version:** kept turns, current question, retrieval calls and results. Preserve call/result adjacency and references. Append volatile data in its proper role instead of editing prior user messages or interpolating it into the static system prompt. Never change the meaning or authority of a message to improve caching.

A permission change or deletion invalidates affected local continuations and prevents their replay, even if it reduces reuse. This is not a claim that changing our payload evicts a provider cache. Do not prewarm by default or choose a longer retention period without explicit host policy and a measured benefit.

## What a runnable example should show

- **Same prefix, new suffix:** identical stable sections as input grows. A local comparison only, not a predicted discount.
- **A compacted or corrected prefix:** tell the extension author where reuse might stop without printing private messages, provider blobs or stable content hashes. An unchanged tool declaration is not a continuing grant of permission.
- **A real receipt, separately:** record normalized input, read and write tokens when observed, and preserve *unknown* for missing fields. A local fake-provider test should never imply measured cache reads, latency or dollars.
- **Budget stays hard:** read/write discounts do not release tokens in context. Reserve room for recall, and recheck actual input after egress and formatting. Avoid frequent compaction at a threshold boundary; record which cap or policy triggered it.

For a later paid canary, replay the same synthetic workload per provider with native projection, a stable brief and appended recall, and a provider-native continuation where implemented. Sample cold start, append, compaction, first turn after compaction, follow-up, and an early edit. Keep model/config constant within each provider, and separate cold and warm trials. Report cache reads/writes, all compaction and recall charges, p50/p95 time to first token, and task correctness. Choose based on cost per correct result, not hit rate: a smaller window with a fresh write can still be cheaper than a large warm one.
